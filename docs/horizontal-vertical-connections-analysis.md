# Анализ горизонтальных и вертикальных связей проекта Dionis Next Level

## 1) Что считалось «вертикальными» и «горизонтальными» связями

- **Вертикальные связи** — поток сверху вниз по слоям: маршруты (`app/[lang]/*`) → словари/бизнес-логика (`app/dictionaries`, `app/lib`) → UI-компоненты (`app/components`) → интеграции (`app/api/*`, внешние сервисы).
- **Горизонтальные связи** — взаимодействие элементов **одного уровня**: страница↔страница, компонент↔компонент, словарь↔словарь, контент↔контент.

## 2) Вертикальные связи (по ключевым пользовательским потокам)

### 2.1 Локализованный shell сайта

1. `app/[lang]/layout.tsx` нормализует язык и формирует общий каркас страницы.
2. В layout подключаются общие «сквозные» компоненты: `Header`, `SiteFooter`, `CookieConsent`.
3. Любая страница в `/[lang]/*` наследует этот каркас и язык.

**Вывод:** это центральная вертикаль «маршрут → общий UI-каркас → дочерний контент».

### 2.2 Главная страница

1. `app/[lang]/page.tsx` нормализует язык.
2. Загружает словари `home` и `agreement`.
3. Передаёт их в `HomeClient`, который рендерит секции и вызывает вложенные компоненты (`ServicesGrid`, `ContactForm`, `BrokerSection`, `DeferredHydration`).

**Вывод:** вертикаль «страница → словари → клиентский контейнер → секционные компоненты» построена чисто и предсказуемо.

### 2.3 Каталог продуктов

1. `app/[lang]/products/page.tsx` определяет язык и активный раздел (`section` в query).
2. Забирает текст из `PRODUCTS_UI` и `HEADER_DICTIONARY`.
3. Рендерит `ProductsDirectoryServer`, затем один из вертикальных срезов (`AutoProductsSection`, `PropertyProductsSection`, и т.д.), после чего `RequestBox`.

**Вывод:** вертикаль «маршрут → dictionary/config → серверная навигация разделов → профильный раздел → CTA». 

### 2.4 Блог и контент

1. `app/lib/blog.ts` читает MDX из `content/blog/<lang>`.
2. Парсит frontmatter, валидирует тип контента, собирает TOC и связанные материалы.
3. Возвращает унифицированную модель статьи для отображения в UI-компонентах блога.

**Вывод:** вертикаль «контент-файлы → контент-пайплайн в lib → UI-блоки MDX» хорошо отделяет редакторский и интерфейсный уровни.

## 3) Горизонтальные связи (между равноправными узлами)

### 3.1 Межстраничные горизонтальные связи

- `Header` связывает ключевые маршруты в одном уровне навигации: home/about/insurance/blog/contacts.
- На главной (`HomeClient`) есть CTA-связки на `/green-card`, `/osago-rf`, `/products`.
- В каталоге продуктов есть горизонтальный переход к `contacts` через `RequestBox`.

**Эффект:** пользователь получает «кольцевую навигацию» между коммерчески важными разделами.

### 3.2 Межкомпонентные горизонтальные связи

- Общие компоненты (`Header`, `SiteFooter`, `CookieConsent`, `RequestBox`) переиспользуются в разных страницах и фичах.
- Внутри продуктовой зоны секционные компоненты имеют одинаковый контракт (`lang`, `base`, `ui`) — это упрощает масштабирование новых разделов.

### 3.3 Межсловарные (i18n) горизонтальные связи

- Языковой ключ (`ru|kz|en`) проходит через страницы, header-словарь, home-словарь и product-словарь.
- Структуры словарей разных доменов синхронизированы через общий `Lang`.

**Риск:** ручная синхронизация полей между словарями может ломаться при росте функциональности.

### 3.4 Контентные горизонтальные связи (blog)

- В frontmatter статей есть явные связи `nextSlugs` и `requiredSlugs`.
- Это даёт управляемую редактором сетку «следующий шаг / обязательное чтение» между материалами.

## 4) Сильные стороны текущей связности

1. Чёткая локализационная ось (`lang`) как единый «сквозной идентификатор».
2. Разделение словарей, UI и контент-пайплайна снижает связность между слоями.
3. Единый layout для `/[lang]/*` удерживает консистентность интерфейса.
4. У блога есть структурные горизонтальные связи на уровне данных, а не «магии» в UI.

## 5) Зоны риска и рекомендации

1. **Дублирование normalize/isLang логики** в нескольких страницах.
   - Рекомендация: вынести общий helper `getLangSafe` в `app/lib/i18n.ts`.
2. **Ручная типизация dictionary-ключей** по фичам.
   - Рекомендация: внедрить compile-time проверки полноты переводов (type-level map или zod-схемы на CI).
3. **Растущая горизонтальная связность Header** (много UI-логики в одном компоненте).
   - Рекомендация: выделить подкомпоненты desktop/mobile menu и hooks для поведения.
4. **Сильная композиция HomeClient** (много секций в одном файле).
   - Рекомендация: декомпозировать по секциям для снижения когнитивной нагрузки.

## 6) Краткая карта связей (итог)

- **Главная вертикаль платформы:** `app/[lang]/layout.tsx` → общие shell-компоненты → конкретные страницы.
- **Продуктовая вертикаль:** `products/page.tsx` → словари и категории → server directory → тематический section.
- **Контентная вертикаль:** `content/blog/*.mdx` → `app/lib/blog.ts` → MDX/UI компоненты.
- **Ключевые горизонтали:** Header-nav, CTA-ссылки между страницами, `nextSlugs/requiredSlugs` между статьями.

## 7) Заключение

Архитектура уже хорошо разделяет вертикальные потоки (роутинг, данные, UI, контент). Главный потенциал улучшения — стандартизировать общие helper-уровни (язык, навигационные конфиги, проверки словарей), чтобы контролируемо расти по горизонтали без дублирования.
