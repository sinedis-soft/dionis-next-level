- Ощущение «реального бизнеса», а не шаблона: **выше среднего**

### Сильные стороны
1. Корректная базовая многоязычная архитектура с языковыми сегментами URL (`/ru`, `/kz`, `/en`).
2. Есть sitemap и robots на уровне Next Metadata API.
3. Внедрён JSON-LD c `Organization`, `WebSite`, `InsuranceAgency`.
4. Есть контентный модуль блога и авторские страницы — база для E-E-A-T.
5. Коммерческие посадочные (green-card, osago-rf, products, contacts) уже разведены.

### Слабые стороны
1. Каноникал и hreflang с `x-default` настроены неполно и местами рискованно для мультиязычия.
2. Глобальный JSON-LD содержит потенциально неверные данные (смешение юрисдикций/контактов) — риск trust-сигналов.
3. Ограниченная SEO-кластеризация: мало «глубоких» long-tail страниц под B2B/B2C интенты.
4. Недостаток доказательной коммерческой части (кейсы, лицензии, верифицируемые факты в масштабируемом формате).
5. Не видно продуманной стратегии на 500–5000 страниц (taxonomy, faceted architecture, canonical strategy под фильтры).

### Критические ошибки
- **P0:** `x-default` указывает на корень сайта (`/`), при том что контент живёт в языковых сегментах — потенциальная неоднозначность для Google по странице по умолчанию.
- **P0:** В JSON-LD есть строка про третьих лиц в Республике Беларусь в тексте согласия (контентно-юридический конфликт для KZ-бренда) и разнонаправленные телефоны/страны, что снижает trust consistency.
- **P1:** Каноникал формируется от `/{lang}` в layout; для вложенных страниц важна строгая согласованность page-level canonical, иначе риск мягких дублей.

### Что снижает доверие Google
- Несогласованность структурированных данных и юридических формулировок по географии/правовым сущностям.
- Недостаток подтверждённого E-E-A-T: экспертные профили, лицензии, регуляторика, референсы, кейсы.
- Слабая «entity completeness» для финсервиса международного профиля.

### Что снижает конверсию
- Формы/CTA присутствуют, но недостаточно «доказательств» до формы (кейсы, SLA, конкретные преимущества, отзывы с атрибуцией).
- Для B2B-сегмента мало страниц под отдельные индустрии и сценарии риска.

## 2) Технический SEO-аудит

## 2.1 Индексация

### robots.txt
- Реализован через `app/robots.ts`: `allow: /`, ссылка на sitemap присутствует.
- Риск: нет точечного disallow для технических URL (если появятся service routes/preview/filter-params).

**Приоритет:** P2.

### sitemap.xml
- Генерация в `app/sitemap.ts`: статические страницы + блоговые статьи + страницы авторов.
- Плюс: есть `lastModified`, `priority`, `changeFrequency`.
- Риск P1: `STATIC_LASTMOD` фиксирован вручную (`2026-05-08`), может устаревать и искажать freshness-сигнал.
- Риск P1: нет image/video/news sitemaps и нет разбивки sitemap index при росте.

### canonical
- В `[lang]/layout.tsx` canonical = `/{lang}`. Для внутренних страниц это нужно переопределять на page-level; если где-то не переопределено, возможна каноникализация всех страниц раздела к корню языка.

**Приоритет:** P0/P1 (проверить все page metadata).

### hreflang и x-default
- Есть alternates на ru/kk-KZ/en и `x-default` на `/`.
- Риск: `x-default` должен указывать либо на selector/lang-neutral страницу, либо на конкретную default-locale версию; текущая реализация неоднозначна.
- Риск: для каждой конкретной страницы нужен симметричный hreflang-набор между эквивалентными URL.

**Приоритет:** P0.

### Дубли, параметры URL, пагинация
- Blog pagination присутствует маршрутом `/blog/page/[page]`.
- Нужна валидация canonical/prev-next/robots для пагинации (в коде не найден единый явный standard-блок).
- Для параметров URL не найдена явная canonical-strategy (на будущее для фильтров каталога).

**Приоритет:** P1.

### Битые ссылки и orphan pages
- Автоматического link graph checker в проекте не обнаружено.
- Потенциально orphan могут появляться в multilingual-блоге/авторах без централизованной перелинковки.

**Приоритет:** P1.

## 2.2 HTML и метатеги

- Title/Description: частично заданы на страницах, но нужна матрица уникальности по всем URL.
- H1-H6: структура в целом есть, но требуется массовая валидация «1 H1 на документ».
- ALT: в ключевых блоках alt есть, но часть изображений/иконок может иметь декоративный характер без системной политики alt="".
- OG/Twitter: точечно есть, но нужна унификация по всем коммерческим страницам.
- Schema.org/JSON-LD: реализовано, но качество данных нужно корректировать (entity consistency, geography/legal coherence).
- Breadcrumbs: компонент есть, но нужно убедиться, что есть schema `BreadcrumbList` в JSON-LD на глубинных страницах.

**Приоритет:** P1.

## 2.3 Core Web Vitals / Performance (оценка по реализации)

### Вероятные плюсы
- Next.js App Router + оптимизация изображений (`next/image`, webp).
- Шрифты через `next/font` c `display: swap`.
- Lazy-подход в отдельных компонентах (`DeferredHydration`).

### Вероятные риски
- Клиентские heavy-компоненты на главной могут ухудшать INP/JS execution.
- Большой объём медиа в `public/` и hero-графика — риск LCP на mobile.
- Сторонние аналитические скрипты в layout (влияние на INP/TTFB при плохой загрузке).

### Что может тормозить
- Избыточная гидратация на landing-блоках, где можно рендерить статично.
- Потенциально тяжёлые изображения hero/partners/service без строгой budget-политики.
- Отсутствие явной стратегии route-level code splitting отчётного уровня (бенчмарков нет).

**Приоритет:** P1.

### Next.js/React-специфичные замечания
- Проверить, что SEO-критичные блоки рендерятся серверно и не зависят от client-only состояния.
- Контролировать hydration mismatches в мультиязычном контенте.
- Следить, чтобы metadata для динамических страниц не оставались только на root/layout уровне.

### Потенциально сильные зоны для ранжирования
- Темы Green Card/OSAGO RF/международные перевозки/регуляторика — при углублении и серийном контенте.

### Что расширять в первую очередь
1. Кластеры B2B: ответственность перевозчика, страхование грузов по направлениям/режимам.

3. TOFU+MOFU+BOFU контент-воронка с чёткой привязкой к заявке.

## 5) Коммерческий SEO-аудит

### Что хорошо
- Есть контактные точки, формы, мессенджеры, продуктовые маршруты.
- Сайт выглядит как рабочий бизнес-проект, а не «визитка на 1 экран».

### Что мешает конверсии
- Недостаточно сильных trust-блоков рядом с CTA:
  - лицензии/регистрационные данные в удобном виде;
  - подтверждённые отзывы;
  - кейсы с результатами;
  - SLA/скорость обработки.
- Не хватает B2B-пруфов: интеграции, процесс сопровождения, KPI обслуживания.

### Почему клиент может не оставить заявку
1. Не видит достаточно доказательств экспертизы именно в своём кейсе.
2. Нет прозрачного «что дальше после отправки формы».
3. Недостаток сравнительных преимуществ против прямого обращения в страховую.

### Где теряются лиды
- Средняя/нижняя часть лендингов без мощных reason-to-believe.
- Сценарии «сложного запроса» без отдельного lead-magnet (бриф-калькулятор/чек-лист).

**Приоритет:** P0/P1.

## Учёт дополнения: BCC Payments Service (как фактор SEO/коммерции)

BCC Payments Service сам по себе не даёт прямого SEO-бустера, но даёт **сильный коммерческий сигнал зрелости**:
- интеграция CRM (Bitrix24) + банк;
- прозрачные статусы платежей/refund;
- эксплуатационная дисциплина (systemd/logging/monitoring).

Как использовать это в SEO/конверсии:
1. Создать публичную страницу «Платежи и безопасность» (B2B trust page) с процессом оплаты, возвратов, SLA и безопасностью.
2. Добавить кейсы «оплата в CRM для корпоративных клиентов» как BOFU-контент.
3. Сформировать SEO-кластер вокруг transactional trust: payment flow, refund policy, security controls.

Приоритет: **P1**.
